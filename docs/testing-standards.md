# TabPlex 测试规范

## 目标

测试只服务两件事：

- 保护核心不变量，降低重构风险。
- 以低成本替代高频、脆弱的手工回归。

如果一个测试做不到这两点，就不应该存在。

## 保留范围

优先保留以下测试：

- 纯逻辑与数据变换。
- URL 归一化、Tab 去重、分组、快照等核心算法。
- 存储解析、迁移、序列化、回填兼容。
- 后台消息协议、状态机、队列、并发控制。
- 真实业务规则的边界条件与异常分支。

这些测试通常满足以下条件：

- 输入输出稳定。
- 契约清晰。
- 重构后仍然成立。
- 失败时能明确指出行为回归。

## 禁止范围

默认不要新增以下测试：

- 读取源码后用正则匹配 JSX、CSS、README、GitHub workflow。
- 只验证 className、静态 HTML 片段、文案是否出现。
- 只为覆盖率数字服务、没有业务含义的测试。
- 依赖内部实现细节、重构后必碎的测试。
- 已经被手工 smoke test 更高效覆盖的低风险 UI 细节。

如果确实要覆盖 UI，必须验证用户行为或稳定契约，而不是源码文本。

## UI 测试规则

当前仓库默认不为纯展示层写静态渲染测试。

只有在以下情况才允许新增 UI 测试：

- 用户交互容易回归，且手工验证成本高。
- 涉及消息收发、异步状态切换、错误回退、禁用态、焦点管理等行为。
- 存在明确的可验证契约，而不是视觉实现细节。

禁止写成：

- `renderToStaticMarkup` 后断言某个 className 存在。
- 读取 `src/*.tsx` 然后匹配 `aria-label` 或某段 JSX 文本。

## 新增测试的判断问题

新增测试前，先回答这 4 个问题：

1. 它保护的是不是高代价回归？
2. 它验证的是不是稳定契约，而不是实现细节？
3. 它是不是比手工验证更便宜、更稳定？
4. 如果未来重构，这个测试是否仍应成立？

只要有两个回答是否定，就不要写。

## 文件组织

- 纯逻辑测试与被测文件同目录放置，使用 `*.test.ts`。
- 只在确有 React 行为测试时使用 `*.test.tsx`。
- 仓库级守护测试应极少存在；除非保护构建发布流程中的真实事故，否则不要添加。
- Manifest 权限、CSP 与 ZIP 内容由发布产物校验脚本和 CI 检查，不要再用读取
  `package.json` 的单元测试重复守护。

## 验证策略

- 改纯逻辑：优先跑对应 Vitest 单测。
- 改后台消息/状态：优先补或改消息协议、状态机测试。
- 改 UI 展示：优先手工 smoke test，必要时再补行为测试。
- 改浏览器集成行为：记录手工验证步骤，不用源码正则测试替代。
- 提交前运行 `pnpm format:check`，让 CI 与本地格式检查保持一致。

## 当前保留方向

当前仓库测试以以下区域为主：

- `src/core`
- `src/features/workspace/logic`
- `lib/workspaceUtils.ts`
- `lib/workspacesQueue.ts`
- `src/background/messages/handlers`

后续新增测试请优先靠近这些高信号区域，不要让测试集合重新膨胀到展示层和仓库文案层。
